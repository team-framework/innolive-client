# Android 방송 녹화와 내보내기

관련 이슈: client #640. iOS 원본 저장([ios-broadcast-recording.md](ios-broadcast-recording.md))과 같은 정책을 따르되
Android는 블러 전 영상과 실제 송출 영상을 함께 저장한다. HTTP·WebRTC 계약은 바꾸지 않는다.

## 녹화 구간

- 방송 시작(golive) 요청 직전에 녹화를 시작하고, 라이브·일시 중지를 확인하면 저장 대상으로 본다. 시작을 확인하지 못한 녹화는 버린다. `BroadcastRecordingCoordinator`가 이 전이를 맡고 녹화 오류는 방송 상태를 바꾸지 않는다.
- 저장 시점은 마지막 대상 종료(방송 상태 종료), `close()`, 새 연결 준비(`start()`), 송출 연결 실패다. 연결 실패(`WebRtcConnectionState.FAILED`)는 송출 경로가 더 이상 방송 상태를 보내지 않으므로 원격 종료 확인을 기다리지 않고 바로 저장한다(iOS `endLocally`). 확인 전 실패는 폐기한다.
- 방송 준비·방송 중에는 설정의 `저장된 방송`(보관함)에 들어갈 수 없고, 열려 있던 보관함은 닫는다(iOS와 같음). 종료 뒤 저장 중에는 들어갈 수 있으며 `영상을 저장하는 중`을 표시한다.

## 입력

| 항목 | 경로 |
| --- | --- |
| 블러 전 영상 | `CameraFrameAnalyzer`의 비식별화·색 보정 전 카메라 프레임. 서버 AI·가림 해제 경로는 송출용 카메라 복사본을 공유(추가 복사 없음), 온디바이스 가림 경로만 따로 복사 |
| 블러 후 영상 | 온디바이스(WebRTC·직접 송출)는 분석기의 가림 처리 출력, 서버 AI는 서버가 돌려주는 원격 트랙. 재협상으로 트랙이 바뀌면 입력을 옮김 |
| 음성 (서버 중계) | WebRTC 음성 처리 모듈의 캡처 후처리 단계(`ExternalAudioProcessingFactory`)에서 에코 제거·잡음 억제 뒤 송출 신호를 복사. iOS `capturePostProcessingDelegate`와 같은 위치 |
| 음성 (직접 송출) | 송출 엔진에 넣는 PCM(대기 화면 무음·음소거 포함). 이 경로는 WebRTC 음성 처리가 없어 엔진 입력이 곧 시청자가 듣는 신호 |

- 음성은 입력 형식과 관계없이 48kHz 스테레오로 바꿔 AAC 128kbps로 저장한다(iOS 고정 형식). 모노는 두 채널에 복사하고 다른 샘플레이트는 선형 보간한다.
- 음성 시간축은 누적 샘플 수로 만들고, 250ms 넘는 콜백 공백은 도착 시각으로 다시 맞춘 뒤 그 길이만큼 실제 무음을 넣는다(iOS `pumpAudio`와 같음, 3ms 이하 흔들림은 무시). 무음은 데이터 없이 인코더 입력에 0을 채운다.

## 인코딩

- 영상은 첫 프레임 크기(긴 변 최대 1920)로 H.264 인코더를 만들고 이후 프레임은 비율을 유지해 맞춘다. 비트레이트는 iOS와 같이 `가로 × 세로 × 4bps`를 2~12Mbps로 제한한다(720p 약 3.7Mbps, 1080p 약 8.3Mbps). 키프레임 1초, VBR, High 프로파일(거부 시 기본), B 프레임 없음은 그대로다.
- MediaCodec·EGL 준비는 첫 프레임을 받은 뒤 녹화 작업 스레드에서 한다. 캡처·분석·디코더 스레드는 기다리지 않고 준비 전 프레임은 누락 수로 센다.
- 블러 전·후 인코더 둘과 AAC 인코더 하나를 추가로 쓰므로 기기 인코더 세션이 늘어난다. 블러 후 인코더만 실패하면 원본만 저장한다.

## 서버 AI 모드의 영상·음성 맞춤

- 서버가 돌려준 영상의 타임스탬프는 서버 왕복·지터 버퍼를 거친 화면 표시 시각이고 음성은 기기 마이크 시각이라, 그대로 저장하면 블러 후 영상이 왕복 지연만큼 늦다. 서버(pion `WriteSample`)는 RTP 시각을 새로 만들고 Android WebRTC는 받은 프레임의 RTP 시각을 넘기지 않아 캡처 시각으로 직접 되돌릴 수 없다.
- `RecordingLatencyEstimator`가 블러 전·후 영상의 프레임 간 움직임 크기(16×16 밝기 격자의 평균 차이)를 시계열로 만들고 0~3초 범위에서 상호상관이 가장 큰 지연을 찾는다. 움직임은 회전·색 보정·얼굴 블러에도 거의 같게 남는다. 상관 0.5 이상·다음 후보보다 0.15 이상 높은 측정만 받아들이고, 정지 장면처럼 측정할 수 없으면 맞추지 않는다.
- 받아들인 측정값의 중앙값을 마무리 때 블러 후 파일의 영상 트랙 시작에서 한 번 뺀다(편집 목록). 재생 속도는 바꾸지 않으므로 녹화 중 지연 변화(지터 버퍼 조정)는 남는다. 측정값은 복구 기록에도 남겨 복구한 파일에도 적용한다.
- 기존 검증의 "음성 시작 오프셋 85ms"는 두 트랙의 시작 시각 차이이며 내용 기준 A/V 동기를 뜻하지 않는다.

## 저장 파일과 복구

- 위치는 앱 no-backup 저장소의 `recordings/<id>/`이며 `original.mp4`(블러 전 + 음성), `processed.mp4`(블러 후 + 음성), `meta.json`, 저장 전 복구 기록 `journal.json`이다.
- 녹화 중에는 조각 MP4(`*.partial.mp4`: 트랙 설명 + 약 1초마다 `moof`/`mdat`)로 쓴다. 두 인코더 형식을 받기 전 출력은 4MB·5초까지만 보관하고, 넘으면 오지 않은 형식에 따라 음성 없음·영상 없음으로 실패한다.
- 저장은 인코더 입력 종료 뒤 최대 3초 기다리고, `Mp4Finalizer`가 다 쓴 조각만 남겨 끝에 표본 표(moov)를 붙인 일반 MP4로 바꾼다. 표본 데이터는 옮기지 않으며 조각 머리는 `skip`, 녹화 중 트랙 설명은 `free`로 바꾼다. 어느 단계에서 멈춰도 다시 실행하면 같은 파일이 된다. 재생 확인 뒤 최종 이름으로 바꾸고 메타데이터를 쓴 다음 복구 기록을 지운다.
- 복구 기록 상태는 iOS와 같다(`provisional`, `confirmed`, `finalizing`, `writer_completed`, `failed`, `aborted`). 보관함을 열 때 메타데이터가 없는 폴더를 이렇게 다룬다.

| 상태 | 처리 |
| --- | --- |
| confirmed·finalizing·writer_completed | 다 쓴 조각까지 일반 MP4로 마무리해 `복구한 녹화`로 목록에 표시 |
| provisional(시작 미확인)·failed(녹화 중 오류)·복구 실패·기록 없음 | 지우지 않고 보관, 개수·용량 표시와 일괄 삭제 제공 |
| aborted·영상 파일 없음 | 삭제 |

- 이 프로세스가 쓰거나 마무리하는 녹화(`RecordingOwnership`)는 보관함이 건드리지 않는다.
- 녹화 시작 전 여유 공간 256MB를 확인한다(iOS 기준). 저장 중 공간 부족은 녹화 실패로 표시한다.
- 저장하는 동안 `BroadcastRecordingSaveService`가 프로세스를 유지한다(iOS background task 대응). 직접 송출의 `DirectBroadcastService`는 `microphone` 타입이고 방송 종료와 함께 멈추며 서버 중계 모드에서는 쓰지 않으므로, 마이크를 붙잡지 않는 별도 서비스를 쓴다. Android 14 이상은 `shortService`(약 3분, 별도 권한 없음), 그 아래는 타입 없이 시작하며 부분 wake lock을 함께 잡는다. 앱이 이미 백그라운드라 시작할 수 없으면 프로세스가 살아 있는 동안만 저장한다.

## 내보내기

iOS 내보내기 시트의 세 동작을 따른다. 항목마다 블러 전·후 영상을 고른 뒤 실행하며, 모두 재인코딩하지 않는다.

| 동작 | 결과 | 복사 |
| --- | --- | --- |
| 영상과 음성 · MP4 공유 | 시스템 공유 시트로 `InnoLive_<시각>_original.mp4` 또는 `_blurred.mp4` | 없음(저장 파일 하드 링크, 실패 시만 복사) |
| 영상·음성 분리 · MP4 + M4A 공유 | 무음 `-video.mp4`와 `-audio.m4a` 두 파일. 앞 빈 구간(시작 오프셋)을 유지 | 트랙별 한 번 |
| 갤러리에 저장 | `Movies/InnoLive`에 MP4 | 한 번(저장 파일에서 바로) |

- 복사가 필요한 동작은 시작 전에 파일 크기 + 32MB 여유 공간을 확인한다. 공유 파일은 FileProvider(캐시의 `recording-shares/`만 노출)로 읽기 권한만 준다.
- 공유 파일은 다른 앱이 늦게 읽을 수 있어 바로 지우지 않고, 하루가 지난 것은 보관함을 열 때, 삭제한 녹화의 것은 삭제할 때 지운다.
- 별도 저장소 권한은 필요 없다. 앱 안 재생과 종료 화면의 재생·내보내기 버튼은 두지 않는다.

## 검증

- 단위 테스트(`com.framework.innolive.feature.live.recording`, 49개): 조각 MP4 쓰기·일반 MP4 변환·임의 지점 중단 복구·중단된 마무리 재실행·트랙 분리 오프셋, 형식 대기·첫 키프레임·역행 시각 버림·메모리 한도와 음성 없음 사유, 세션의 입력 종료 시간 제한·블러 후만 실패·작업 스레드 준비·무음 채움·실패 보관, 복구 기록 상태별 복구·보관·삭제, 48kHz 스테레오 변환·후처리 탭, 지연 측정, 전이·비트레이트·파일 이름.
- androidTest(기기 전용, 미실행): `BroadcastRecordingLifecycleTest`(연결 실패 즉시 저장·재연결 중복 저장 없음·트랙 교체·close 저장), `BroadcastRecordingDeviceTest`(실제 MediaCodec 녹화의 플랫폼 파서 확인·중단 복구·분리 파일).
- 실제 기기에서 각 모드 녹화 재생, 서버 AI 블러 후 영상의 콘텐츠 A/V 동기와 지연 측정값, 음성 처리 후 신호 녹화, 강제 종료 뒤 복구, 저장 중 백그라운드 유지, 공유 시트·갤러리 저장, 인코더 세션 한도, 장시간 녹화 발열과 용량은 미검증이다.
