# YouTube viewer chat v1

- `targets[]` can include optional `video_id` for YouTube after preparation. CHZZK and unprepared targets omit the key. Older responses without the field remain valid.
- Source: server `internal/session/manager.go` at `c6276d9db8d519703e1ba0ae660a398e19e2ad79`, `StreamTargetState.VideoID` and snapshot assignment from `platformBroadcast.BroadcastID`. Server main provides the field; production deployment has not been checked.
- iOS renders viewer chat directly at the bottom-left of the broadcast preview, above the measured broadcast controls in portrait. On compact-height iPhones, chat stays at the bottom-left, broadcast controls occupy at most 400pt on the right, and camera tools form a horizontal row at the top-right. A chat menu below the messages toggles their visibility without opening a separate chat sheet. Hiding removes native message rows from the UI and accessibility tree while the receiver remains active. Before a YouTube broadcast starts, for unsupported targets, or while the video ID is missing/invalid, the panel explains availability. A valid live video ID automatically replaces the explanation with chat. Paused broadcasts retain chat; stopped/removed targets and cleared sessions remove the web content. Face selection temporarily hides the panel, and the local camera preview reserves space above it.
- Chat loads `https://www.youtube.com/live_chat?is_popout=1&v=<video_id>` using URLComponents. A changed ID replaces the receiver and clears the previous native messages. Removing the chat content stops loading and clears the WebView.
- An ephemeral unauthenticated WKWebView receives the YouTube chat document in desktop mode with a Safari user agent. The receiver is not visible or interactive. An isolated-world MutationObserver extracts message IDs, author names, text, and emoji alt text into native SwiftUI rows. No InnoLive access token, owner token, or persistent browser cookies enter it. Login, links, forms, new windows, non-HTTPS and other-document navigations are blocked. Resource requests remain handled by WebKit.
- Private, age-restricted, disabled-chat, consent-gated, and region-dependent YouTube pages may not show messages. Public/private broadcast display remains a manual verification item. Unlisted live reception was verified on the iPad and iPhone below; fixture tests do not assert live YouTube availability.
- Android renders the same overlay on the live screen's basic page under the iOS rule (YouTube target with `broadcast_phase` `live`, `status` other than `stopped` including direct-publish `idle` and unknown values, and a valid 11-character ID): bottom-left above the measured broadcast controls, to the right of the camera-tool band in landscape, 280dp wide with 136dp/106dp message areas, initial-avatar rows, and a 44dp chat menu that hides or shows the rows while reception continues. A WebView with a desktop Chrome user agent loads the same `live_chat` document behind the broadcast video, never receives InnoLive tokens, and posts the iOS extraction script's JSON through `WebViewCompat.addWebMessageListener` limited to the `https://www.youtube.com` main frame (`@JavascriptInterface` only when unsupported). Payloads over 512,000 bytes or from another document are dropped. Android WebView shares the app-wide cookie and WebStorage; the receiver disables third-party cookies, blocks main-frame form submissions, and clears YouTube-domain cookies and WebStorage when the receiver is removed, on logout, and on account deletion. See `docs/android-viewer-chat.md`.
- Existing clients ignore `video_id`. This is an additive response-only change with no request or signaling changes.

- The overlay uses the Dynamic Type footnote style (13pt at the default size), a maximum width of 280pt, and a message area height of 136pt in portrait or 106pt in compact landscape, followed by a 44pt visibility menu with 4pt spacing. Rows use 8pt horizontal and 5pt vertical padding. The overlay shows individual translucent message rows, with a circular author initial, a bold white author name above a wrapping body, and a translucent background. It keeps the latest 50 messages and follows new arrivals. Empty/deleted entries are omitted; old-video callbacks cannot replace current messages. Text is rendered as text, never HTML. YouTube DOM selectors are an external dependency and need live checks after upstream changes.
- A loaded page that does not expose the chat renderer within 12 seconds shows a retry action instead of an indefinite spinner.

## Manual acceptance

- Confirm the chat panel appears at the bottom-left before broadcasting and the chat visibility menu appears below messages while live.
- Start a public YouTube broadcast and verify messages appear automatically without opening a sheet.
- Pause/resume and confirm chat remains. End/remove YouTube and confirm the web content clears.
- Change video ID and confirm the panel reloads the new broadcast. Retry a failed load.
- Check iPhone 16/16 Pro sizes and iPad: chat must remain above broadcast controls and not cover the local camera preview.
- Verify private broadcasts and consent pages separately; the viewer WebView does not authenticate.

## Verification (2026-10-19)

- 10 chat policy/WebView tests and 2 message bridge tests passed on the simulator. The bridge test loads local HTML into a real WKWebView and checks body text, emoji, text updates, deletion, stale-video rejection, and cleanup. This fixture is not proof of live reception.
- Two rendering tests passed at 393×852pt (iPhone 16) and 402×874pt (16 Pro). Light/dark screenshots show separate native rows and long Korean text wrapping. Test messages are fixtures.
- Signed device build installed and launched on iPad Air 13-inch (M3), iPadOS 26.6. An unlisted YouTube broadcast received two real browser-posted messages as separate native rows: a short Korean message with an emoji and a long Korean message wrapping across four lines. A device UI test asserted both complete message bodies, ended the broadcast, and verified that all message rows cleared (1 test passed).
- Earlier WebView-only live checks exposed two real failures: YouTube rejected the default browser identity, then the small embedded page obscured message bodies. The Safari identity and native message rows address those separately.

- Live test preparation initially failed twice with `YouTube: Could not process the YouTube request.` After the user authorized deleting an existing PRISM broadcast, a new preparation and Go Live succeeded. The underlying error code was not captured, so the cause is not established.

- iPhone 16 Pro (402×874pt) received two real messages in a new unlisted broadcast. The device UI test passed with two separate native rows and complete Korean/emoji labels. The long message wrapped across four lines; screenshots showed no clipping or overlap with broadcast controls or the local camera preview. This initial device check covered portrait orientation; the later compact-layout check below covers landscape.

- Compact layout follow-up: signed build installed on iPhone 16 Pro and a new unlisted broadcast started in landscape. Device screenshots confirmed separate left chat and right control regions, with camera tools above the controls. After reconnecting the browser, short and long comments appeared in native rows without overlapping the broadcast buttons.
- Compact layout rendering tests passed at iPhone 16 portrait, iPhone 16 Pro portrait, and iPhone 16 Pro landscape sizes (3 tests, light/dark screenshots). The fixture uses its available geometry to avoid cropping controls at the landscape viewport boundary.

- Reference-layout follow-up: three light/dark rendering tests passed after changing rows to an initial avatar and stacked author/body text. A signed build on iPhone 16 Pro received two real comments in landscape; the device UI test passed assertions for full long-message visibility, no intersection with broadcast/camera/chat buttons, zero native message nodes while hidden, and both messages restored after showing chat again.
